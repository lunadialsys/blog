We have been enamored with the Lua language for well over ten years; it's a really interesting, powerful and flexible language.
Lua is the reason we learnt how to code! It led us everywhere that we are now. And part of this was, no doubt, thanks to its slightly quirky, but incredibly deep architecture,
that allows for a level of control that you really don't see in many other domains of programming.

One of the crucial components of Lua's flexibility, in our opinion, is the concept of _upvalues_.
This is a word that you may have seen before, in Lua circles, but its meaning may seem slightly nebulous at first; it's not a concept other languages have.

However, don't worry, because upvalues are actually really simple to grasp! ...But to talk about them, we first have to talk about _closures_.

## Closures and you
Let's take the following code:
```lua
local n: integer = 1
local function increment_it()
    n = n + 1
end

print(n)
increment_it()
print(n)
```

When we run this program, we get the output of `1, 2`.
When we think about what `increment_it` is doing, it's taking a variable from outside, and modifying its value.
It "captures" the variable `n`; we refer to that action of capturing a variable as _closing over_ it, and a function that does so as a _closure_.

Any function that closes over at least one value is a closure; they don't have special semantics or syntax within Lua.
You've probably written closures before, and not even been aware of it!

Closures respect the usual scoping rules when it comes time to find their values:
```lua
do -- This works:
    local n: integer = 1
    local function increment_it()
        n = n + 1
    end
end

-- ...but this won't even compile as Teal:
local function increment_it()
    n = n + 1 -- unknown variable: n
end

-- If you run this as Lua, here you would get an error:
increment_it() -- attempt to perform arithmetic on a nil value (global 'n')
```

Nested functions will "walk" the scope upwards, to find the value to close over:
```lua
local n = 1
local function one(): function()
    local function two()
        n = n + 1
    end
    return two
end

local two = one()
two()
print(n) -- prints '2'
```

And it doesn't matter how much later a closure runs; the values it closes over are still going to be there. They won't fall out of scope so long as the function itself exists.
The specifics of where closure values end up are a bit odd; they don't hang around the "true" scope forever,
instead they live in their own world only accessible to the function they belong to; we'll talk about this more later.


## What's upvalue?
_~~Nothing much, what's up with you?~~_

With that little detour out of the way, we can finally talk about upvalues proper.

...The word "upvalue" refers to any value that is being closed over by a closure. `n` in our examples is an upvalue.
Pretty anticlimactic, huh? But that's what I mean by it being a really simple concept.
However, upvalues, when used well, can be incredibly powerful, and allow for some really flexible code.

For instance, when constructing a metatable-based proxy object:
```lua
local function wrap_it(source: {any:any}): table
    local proxy = {}
    setmetatable(proxy, {
        __index = function(_, key): any
            return rawget(source, key)
        end,
        __newindex = function(_, key, value)
            rawset(source, key, value)
        end
    })
    return proxy
end
```
We don't have to do anything special, because the metamethods on `proxy` can just grab the `source` straight out of the arguments, as an upvalue,
because arguments are just automatically-defined local variables.

Constructing wrapper proxy objects like this is something I do surprisingly often!
In this regard, upvalues are one of our favourite features in the entire language, because they allow this and much more.


## Cause for concern
Take the following code:
```lua
local n = 1
local function get_value(): integer, function()
    local function increment_it()
        n = n + 1
    end
    return n, increment_it
end

local the_number, increment_it = get_value()
print(the_number) -- 1
increment_it()
print(the_number) -- 2, right?

-- ...now fetch and print it again
the_number = get_value()
print(the_number) -- 3...?
```

What do we see when we run this program?

You may expect to see `1, 2, 3`, but **that's not what happens**: we actually get `1, 1, 2` instead.

This is because our variable `n` is closed over by the `get_value` function, creating an upvalue called `n`; and then,
**that upvalue** is closed over by `increment_it`, defined on the inside of `get_value`. `increment_it` is _not_ modifying the `n` that we defined in the outer scope,
but is modifying _the upvalue_ `n` that belongs to `get_value`, which is why calling `get_value` a second time returns `2`; we have to fetch the updated value from the function it belongs to.[^1]

You probably won't ever run into a situation where this matters; this code is pretty hard to reason about, so this isn't a pattern that comes up very often.
However, it _is_ a thing that can happen, so, uh, be careful I guess.


## Debug, debug, debug
The `debug` module is one of the most interesting parts of Lua; it contains many functions that allow you to completely violate the rules of the language.
In this regard, I tend to treat the `debug` module much like one would treat `unsafe` in Rust; it's not something you normally go near, it's not something you _need_,
_but when you do need it, you know you need it, and it saves your life._

`debug` is commonly removed from sandboxed Lua environments, for reasons that will become apparent very shortly.


## Get and set
The two simplest functions within `debug` for dealing with upvalues are `debug.getupvalue` and `debug.setupvalue`.
As their names imply, they enable you to _directly_ retrieve and modify the values of upvalues, without caring about what function they belong to,
or even if it makes sense for you to be able to access them.

They allow you to modify values that aren't even in your own scope at all:
```lua
local function factory(): function(): integer
    local the_value = 0
    return function(): integer
        the_value = the_value + 1
        return the_value
    end
end

local n = factory()
n()
-- we forgot to assign the return value to a variable! how do we get the value...?

-- oh, right:
local name, value = debug.getupvalue(n, 1)
print(name, value)

debug.setupvalue(n, 1, 4)
print(n())
```
This program prints `the_value, 1` and then `5`.
As you can see, even if we aren't able to access the value directly, we can reach into the fabric of the universe and access it anyway.
This also demonstrates how upvalues live in their own magic world, and that even if inaccessible, their values are preserved.

Of course, this opens the door for all sorts of nonsense! As _a lot_ of sandboxes for Lua code are, themselves, written in Lua
(I'll talk more about how that's possible in a bit), this allows for a very easy way to poke a hole straight through
the carefully-constructed veil of safety. Hence, `debug` is **very dangerous** and almost always removed in the environments of untrusted Lua code.


## Together forever
Identically-named upvalues are not the same, because upvalues are tied to scope and not name. For instance:

```lua
local function factory(): function(): integer
    local the_value = 0
    return function(): integer
        the_value = the_value + 1
        return the_value
    end
end

local one, two = factory(), factory()
assert(one ~= two)

print(one(), two())
```

`one` and `two` are not the same function, and they both close over a value named `the_value`,
but the values they close over refer to _different variables_. There's two variables, both named `the_value`, and they aren't the same,
so this program will print `1, 1`. From now on, I'll refer to the concept of "the specific local variable my upvalue is referring to" as an _upvalue reference_.
(You can think about it as a pointer.)

There may be rare occasions where this isn't what you want; there's a tool to solve this, `debug.upvaluejoin`.
That function copies across an upvalue reference from one function to another, so "joining" them together.
You can use it to join the behaviour of two functions; let's modify the previous example:
```lua
local one, two = factory(), factory()
-- debug.upvaluejoin(to, to_index, from, from_index)
debug.upvaluejoin(two, 1, one, 1)

print(one(), two())
```

This program now prints `1, 2` because the first upvalue reference of `two` is now the same as the first upvalue reference of `one`, so
they are both pointing to the same variable, and thus, modifying the same value.


## Can I see your ID?
There is one more upvalue-related function in the `debug` table, `debug.upvalueid`. It isn't terribly useful, so I'll be brief.

This function does exactly one thing: returns the actual upvalue reference at the specified index for the function you give it.
That's to say, if two functions refer to the same local variable, `debug.upvalueid(one, index) == debug.upvalueid(two, index)` will be true.

What `debug.setupvalue` actually returns is... uh, a raw pointer. Well, more specifically, a type called a "light userdata",
which is itself just a C pointer. Unfortunately, you can't do anything too interesting with these from the confines of just Lua,
even with the other methods inside of the `debug` table.[^2]


## `string.dump`
Yeah, this function isn't part of the `debug` table at all. However, I still think it's important to bring up how it interacts
with upvalues; well, rather, how it _doesn't_.

`string.dump` is a standard-library function that dumps a Lua function into bytecode form.[^3]
It's situational, but useful when you need it; the bytecode it produces is the same as the one produced by `luac`,
the standalone command-line compiler that probably came with your Lua installation.

Bytecode returned by `string.dump` can be loaded with, well, the function called `load`, but - since it's a newly-created function - all of the
loaded function's environment will be reset. This includes upvalues; `string.dump`ing a function will not preserve any of the upvalue references it has.
Their _names_ will be kept, but not the data they hold.

Now, `string.dump` actually takes _two_ arguments: the function, and an optional boolean called `strip`, which causes
it to produce significantly less bytecode... _but_ at the cost of losing the names of all of the function's upvalues.
Losing the upvalues' names means that `debug.getupvalue` will always return a "no name" value as its first return value.

We can prove this easily with the following code:
```lua
local function factory(): function(): integer
    local the_value = 0
    return function(): integer
        the_value = the_value + 1
        return the_value
    end
end

local n = factory()
n()

local name, value = debug.getupvalue(n, 1)
print(name, value)

local n2 = load(string.dump(n, true))
local newname, newvalue = debug.getupvalue(n2, 1)
print(newname, newvalue)
```

`n2` here is a copy of our `n` function, so it should have the exact same upvalues.
We can verify this by running the program, and when we do, we get the output of `the_value, 1` as we expect,
and then... uh, `(no name), table: <some pointer>`.

...Wait, _what?_ Excuse me? _Table?_


## The ghost of `setfenv` past
If you've been around the Lua block for a while, you probably know that in older versions of the language,
there used to be a pair of functions called `setfenv` and `getfenv`. These stand for "**set**/**get** **f**unction **env**ironment",
but haven't been relevant for a while, as they were removed from the standard library. They were quite powerful, as
they allowed the Lua programmer to completely override the environment of an individual function, walling it off from the rest of the program.

As a Lua programmer, you're probably also aware of the `_G` table: the global environment for the whole program.
All globals defined in the program end up in there, and the whole of the standard library also exists within it.
`_G` has existed since at least Lua 5.1,[^4] but what you might not know is that - in newer versions of Lua - it has a cousin.

In Lua 5.2, the way that the global environment worked got redone; while previously you could just use `setfenv` and `getfenv` to control the environment,
5.2 cut both of them _entirely_. This presented an issue, as sandboxing was done with setfenv; of course, there had to be a replacement.

So, enter `_ENV`.

`_ENV` is a table that contains the current function's _local_ environment. Instead of modifying the entire global environment,
using `_ENV` lets you modify what resources a function has access to on a granular basis. It works like this:
```lua
local function test(): function() | nil
    local _ENV = {}
    return print
end
print(test())
```
You'll get `nil` here, because the function's environment has been overwritten, and so the `print` function stopped existing within it.
We can use it again outside of the `test` function, because environments are lexically scoped; when we leave the function's scope,
we also leave its environment, and return to its previous one as the stack unwinds. In this case, that's the default global environment.

...But, wait, if I said `_ENV` is a table, why are we defining it with `local`? Shouldn't it already exist, like `_G` does?

Well, uh, you might already have been able to see where I'm going with this, but... yeah, the environment is an upvalue.

More specifically, `_ENV` is an upvalue of any function _that refers to any global variable_. That part's important,
because a function that _doesn't_ refer to any global variables _will not have an upvalue reference to an `_ENV`_. 
What actually happens is that when resolving the function's environment, Lua walks the stack upwards and uses the
_first_ `_ENV` it finds, i.e. the one in the closest scope to the scope accessing the global.
Usually, this is the `_ENV` that is automatically defined by Lua when it loads the initial chunk, which results in
the scope's environment being the global environment that we're all used to.

When creating a new chunk, you can use the fourth argument of the `load` function to control the `_ENV`:
```lua
local v = load('return f', '', 't', {f = 25} as table)
print(v()) -- 25
```

More or less, what load does in this case is this:
```lua
-- this is not real code because `load` is implemented in C
local function load(src: string, fn: string, mode: string, env: table)
    -- ...
    local _ENV = env
    return function(...)
        -- ...
    end
end
```

Knowing that `_ENV` is just an upvalue, we can reimplement `getfenv` as follows, by just searching through the function until we find it.
```lua
local type AnyFunction = function(...: any): any...
local type Environment<T> = {string:any}
local function getfenv<T is AnyFunction>(func: T): Environment<T> | nil
    local n = 1
    local name, value: string, any
    repeat
        name, value = debug.getupvalue(func as function(), n)
        if name == '_ENV' then
            return value as Environment<T>
        end
        n = n + 1
    until not name
end

global number = 0
local function test()
    number = number + 1
end
print(getfenv(test) == _G) -- true
```

Pretty straight-forward, huh? That does still leave the problem of `setfenv`, though.


## The ghost of `setfenv` present
We can't talk about getfenv without talking about setfenv, so let's do as we did previously, and try to reimplement it.

Of course, if getting the environment was just as simple as scanning through the upvalues until we find the right one,
it would logically follow that directly controlling the environment is as simple as doing something like this:
```lua
local function set_env(func: function(), new_env: table)
    local n = 1
    local name: string
    repeat
        name = debug.getupvalue(func, n)
        if name == '_ENV' then
            debug.setupvalue(func, n, new_env)
        end
        n = n + 1
    until not name
end

local function test()
    print('test!')
end
set_env(test, {
    print = function(n: string)
        print('got our value: ' .. n)
    end
})
print('testing:')
test()
```

Well, if you run the above program, you'll quickly find a problem. Rather, the problem is quite _slow_, because the program will spin for a while,
before dying with a stack overflow error. So we're causing infinite recursion somehow.

The easy answer here is that by calling `print` within `print`, inside our `print` function Lua finds the local environment, finds `print` within it and calls it,
which would seem like a perfectly plausible explanation for why this is an infinitely-recursive loop.
...But that's also not what's happening here, because our new `print` function isn't defined inside of the scope of the `test` function, so the environment doesn't apply to it.
No, the real problem is significantly sneakier.

The actual problem is that _upvalue references can be shared between functions_, as we touched on earlier when we went over `debug.upvaluejoin`.
The interpreter takes the easy route and doesn't _copy_ the environment into the new function's upvalue, instead it just grabs a _reference_ to it.
So, by editing the `_ENV` of our `test` function, we're inadvertently editing _our own global environment_, because that's what it points to.
That means we've successfully overwritten our global environment with one that holds nothing except a `print` function that calls itself forever;
the infinite loop doesn't even occur inside of `test`, it occurs in the call to `print` right before it.

So we can't use `debug.setupvalue`, because if we modify the value, we'll affect _everything_. We need to rewrite its reference.
...And that's exactly what `debug.upvaluejoin` does; it rewrites upvalue references to point to other values.

The problem still remains, though, that we can't magic an upvalue out of thin air, it has to come from somewhere,
because `debug.upvaluejoin` takes two functions as its arguments. The solution there is very simple; we can just use a
_lambda_/anonymous function that closes over a value we control. If we don't refer to any globals within it, it won't have an `_ENV`,
and we can know that our chosen value will end up in its upvalue slot 1.

With this newfound knowledge, we have all of the pieces that we need to create our own `setfenv`.[^5]  
Here's mine:
```lua
local type AnyFunction = function(...: any): any...
local type Environment<T> = {string:any}
local function setfenv<T is AnyFunction>(func: T | integer, new_env: Environment<T>): AnyFunction | nil
    local n = 1
    local name: string

    -- setfenv's first argument can be either a function or a stack index:
    local target: function()
    if type(func) == 'function' then
        target = func as AnyFunction
    else
        local i = func as integer
        local fn = debug.getinfo(i + 1, 'f')
        target = fn.func as AnyFunction
    end
    if not target then return nil end

    -- never called; this function only serves as upvalue storage
    -- and returns `new_env` so we can be sure it closes over it
    local helper = function(): any return new_env end

    repeat
        name = debug.getupvalue(target, n)
        if name == '_ENV' then
            debug.upvaluejoin(target, n, helper, 1)
        end
        n = n + 1
    until not name

    return target
end

local function test()
    print('test!')
end
setfenv(test, {
    print = function(n: string)
        print('print called: ' .. n)
    end
})
print('testing...')
test()
```

And if we run this program, sure enough, we see `testing... print called: test!`, just as we would expect.
The function `test`'s environment contains nothing (not even `_VERSION`) aside from our replaced `print` function. Success!
